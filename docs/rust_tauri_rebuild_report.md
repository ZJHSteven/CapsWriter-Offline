# CapsWriter-Offline Fork 现状链路与 Rust/Tauri 重构报告

## 1. 文档目的

这份文档不是泛泛介绍整个仓库，而是只围绕你当前真实使用的两类需求，整理出一份可直接喂给编码 AI 的“高密度工程上下文”：

1. 快捷键实时语音输入  
2. 文件/视频转文字

目标不是继续在 Python 项目里做大改，而是把“当前系统到底怎么工作、哪些功能真在用、哪些只是仓库里存在但对你现在不重要”讲清楚，为后续新建 `Rust + Tauri` 项目做边界冻结。

---

## 2. 当前结论

### 2.1 你当前真正依赖的业务能力只有两条

1. 实时语音输入链路  
按下快捷键开始录音，松开后结束；音频走本地客户端与本地服务端，再由服务端接入阿里云百炼实时 WebSocket，最终回到客户端做热词替换并上屏。

2. 文件转写链路  
把音频/视频文件拖到 `start_client.exe` 上，程序因收到启动参数而进入“文件模式”；然后做音频预处理、上传、调用百炼 REST 异步转写，最后落盘成 `.txt/.json/.srt`。

### 2.2 当前最重要的结构性事实

1. 麦克风实时链路仍然是“本地客户端 + 本地服务端”的双进程结构。
2. 文件转写链路已经独立，不再依赖本地实时服务端 WebSocket。
3. 热词替换只发生在“麦克风最终识别结果回到客户端之后”，并不参与文件转写结果处理。
4. 你没在用 LLM，但当前默认配置下它仍会初始化；只是如果语音开头没有匹配角色前缀，最后会退化成普通输出。
5. 这个仓库几乎没有成体系的自动化测试，当前验证方式主要是手工联调、日志观察、少量 `py_compile` 级别检查。

### 2.3 对 Rust/Tauri 重构最关键的判断

如果你后面要做新项目，最合理的目标不是“把现有 Python 文件逐个翻译成 Rust”，而是：

1. 把实时输入和文件转写抽象成两个独立服务模块。
2. 去掉“本地客户端 <-> 本地服务端”这层历史中转，改成单个 Tauri 应用内部的 Rust 后端任务。
3. 用 Tauri 前端只承载设置页、日志页、文件拖放入口、状态显示。
4. 把快捷键、音频采集、云端 ASR、文本输出这些真正需要系统权限和性能的部分放在 Rust 侧。

## 3. 当前项目的真实入口

### 3.1 客户端入口

- `start_client.py`
- `core_client.py`

逻辑非常简单：

1. 如果 `sys.argv[1:]` 非空，就走文件模式。
2. 如果没有参数，就走麦克风模式。

这意味着你说的“把文件拖到 client 上转写”，本质并不是项目里有一个复杂拖拽界面，而是 Windows 把文件路径作为启动参数传给客户端。

这对重构非常重要，因为它说明：

1. 文件转写并不依赖复杂 GUI。
2. 新的 Tauri 项目可以非常容易地用“拖放文件到窗口”或“命令行参数”替代当前体验。

### 3.2 服务端入口

- `start_server.py`
- `core_server.py`

服务端负责：

1. 启动识别子进程
2. 启动本地 WebSocket 服务器
3. 接收客户端发来的麦克风音频数据
4. 调用云端实时识别
5. 把结果回推给客户端

## 4. 链路一：快捷键实时语音输入的完整调用链

这一条链路是你当前日常最核心的功能。

### 4.1 启动阶段

入口文件：

- `core_client.py`
- `util/client/startup.py`

启动后会做这些事：

1. 初始化全局状态 `ClientState`
2. 初始化托盘
3. 加载热词文件并开启文件监视
4. 初始化 LLM 系统
5. 打开麦克风音频流
6. 启动全局快捷键监听
7. 可选启动 UDP 控制

这里要特别注意：

1. 虽然你没在实际使用 LLM，但 `Config.llm_enabled = True` 时它会在启动阶段初始化。
2. 热词相关文件会被持续监听，修改后自动重载。

### 4.2 按键触发录音

关键文件：

- `util/client/shortcut/shortcut_manager.py`
- `util/client/shortcut/event_handler.py`
- `util/client/shortcut/task.py`

当前默认快捷键配置在 `config.py`：

1. `caps_lock`
2. 鼠标侧键 `x2`

长按模式下的实际流程：

1. 监听器捕获按键按下。
2. `ShortcutTask.launch()` 被调用。
3. 向客户端输入队列写入一条 `type='begin'` 的事件。
4. 创建一个 `AudioRecorder.record_and_send()` 异步任务。

按键松开后：

1. 如果按住时间小于阈值 `Config.threshold`，就取消录音并补发原按键。
2. 如果达到阈值，就写入一条 `type='finish'` 事件，结束当前录音任务。

### 4.3 麦克风采集

关键文件：

- `util/client/audio/stream.py`

当前实现细节：

1. 使用 `sounddevice.InputStream`
2. 采样率固定 `48000 Hz`
3. 回调块大小固定 `50 ms`
4. 只有 `state.recording = True` 时，音频回调才会把数据送入队列

这说明当前 Python 客户端内部真实采集格式是：

1. 本地采集：`float32`
2. 采样率：`48k`
3. 声道：单声道或双声道，取决于设备

### 4.4 客户端录音任务如何把数据发给本地服务端

关键文件：

- `util/client/audio/recorder.py`
- `util/client/websocket_manager.py`

`AudioRecorder.record_and_send()` 的关键逻辑：

1. 为整次录音生成一个 `task_id`
2. 等待 `begin / data / finish` 三类队列事件
3. 在阈值前先做本地缓存，避免短按误触时发出去
4. 真正开始后，把 48k 采样数据降到 16k，并转为单声道
5. base64 编码后通过本地 WebSocket 发送给服务端

当前降采样与单声道处理方式很朴素：

1. 用 `data[::3]` 做 48k -> 16k 抽取
2. 再对通道做 `np.mean(..., axis=1)` 合并成单声道

这意味着新项目里必须非常明确处理以下问题：

1. 音频采集格式
2. 重采样策略
3. 单声道混音策略
4. 发送分帧粒度

### 4.5 本地服务端如何接住这些音频

关键文件：

- `core_server.py`
- `util/server/server_ws_recv.py`
- `util/server/service.py`

服务端会启动一个本地 WebSocket Server。

客户端发来的消息包含这些核心字段：

1. `task_id`
2. `is_final`
3. `time_start`
4. `time_frame`
5. `source`
6. `data`

在 `aliyun_realtime` 模式下，服务端不会再做过去那种“60 秒工程切段 + 本地拼文本”，而是：

1. 只把客户端发来的音频数据解码出来
2. 再按传输层固定 `100ms` 分帧
3. 把每一帧作为识别任务送到麦克风队列
4. 最后用一个空数据的 `is_final=True` 任务表示“这次会话结束了”

### 4.6 识别子进程如何接入阿里云百炼实时 WebSocket

关键文件：

- `util/server/server_init_recognizer.py`
- `util/server/asr_aliyun_realtime.py`

这是当前实时链路的核心。

当前设计已经不是“每个片段独立识别再拼接”，而是：

1. 一个本地 `task_id`
2. 对应一个完整的云端实时会话

核心状态机规则：

1. 客户端持续送音频帧
2. 服务端持续把这些帧转成 PCM16 发给百炼
3. 云端不断回 `result-generated`
4. 本地根据 `begin_time` 识别“是不是同一句的修正版”
5. 对同一句做覆盖更新，而不是盲目追加
6. 只有在 `sentence_end=true` 或 `end_time!=null` 时才把这句标成定稿
7. 松键后发送 `finish-task`
8. 等 `task-finished`
9. 再一次性汇总最终文本返回给客户端

这个状态机是整个云端改造里最有价值、最需要迁移到 Rust 的核心知识。

### 4.7 为什么这套状态机必须保留

原因很简单：

1. 百炼实时返回的 `result-generated` 不是“稳定增量”
2. 它更像“当前句子的最新快照”
3. 如果你把每次回包都直接追加，就会出现重复文本

所以 Rust 重构时不能偷懒写成：

1. 收到一条结果就 `total += text`

而必须保留现在这个概念：

1. 句子状态机
2. 句子按 `begin_time` 归档
3. 同句覆盖
4. 定稿后才能真正并入最终结果

### 4.8 失败保底与自动重试

关键文件：

- `util/server/asr_aliyun_realtime.py`
- `util/server/failed_task_store.py`
- `retry_failed_tasks.py`

当前实时云端链路已经做了比较重的“稳健性止血”：

1. 整次会话 PCM 会临时落盘
2. 如果最后 `task-finished` 没等到，已定稿内容不会全丢
3. 失败任务会保存到 `runtime/failed_tasks/...`
4. 可以尝试自动重试一次
5. 也可以后续手动重试

这部分不是“表面功能”，但它对真实可用性影响很大。

如果 Rust 新项目想先做最小版，可以先不做完整失败任务仓库，但至少要保留：

1. 会话级临时音频缓存
2. 失败时的保底文本
3. 可靠的 finish 超时处理

### 4.9 结果回到客户端后的后处理与上屏

关键文件：

- `util/server/server_ws_send.py`
- `util/client/output/result_processor.py`
- `util/client/output/text_output.py`

当前客户端只对 `is_final=True` 的结果做正式处理。

然后按顺序做这些动作：

1. 如果是失败保底结果，只打印，不自动上屏
2. 可选繁体转换
3. 热词音素纠错
4. 规则替换
5. 去掉末尾标点
6. 可选 LLM 角色处理
7. 输出文本
8. 写文字备份
9. 可选重命名录音文件
10. 可选 UDP 广播

真正和你当前使用强相关的是：

1. 热词替换
2. 文本输出

#### 文本输出当前有两种方式

1. `keyboard.write(text)` 模拟打字
2. `pyclip.copy(text)` 后模拟 `Ctrl+V` 粘贴

默认配置是：

1. `paste = False`

也就是默认直接模拟键盘输入，而不是走剪贴板粘贴。

## 5. 链路二：文件转写的完整调用链

这一条链路和实时输入已经明显解耦。

### 5.1 入口与触发方式

关键文件：

- `start_client.py`
- `core_client.py`

当有启动参数时，客户端进入 `main_file()`。

这条链路不是 GUI 内部调用，也不是发给本地服务端处理，而是客户端自己直接做完整文件转写。

### 5.2 文件模式的实际流程

关键文件：

- `util/client/transcribe/file_transcriber.py`
- `util/client/transcribe/file_upload_resolver.py`
- `util/client/transcribe/dashscope_rest_client.py`

流程如下：

1. 检查文件存在、API Key、FFmpeg、上传模式配置
2. 如果启用了预处理，就用 FFmpeg 把输入文件转成 `16k 单声道 wav`
3. 把本地文件上传成可访问 URL
4. 提交百炼 REST 异步任务
5. 轮询 `task_status`
6. 解析结果
7. 保存 `.txt/.json/.srt/.merge.txt`

### 5.3 当前默认上传模式

配置文件：

- `config.py`

当前默认：

1. `file_transcribe_backend = 'aliyun_rest'`
2. `file_upload_mode = 'dashscope_temp_oss'`

也就是：

1. 先调用百炼上传凭证接口 `getPolicy`
2. 用返回的表单字段上传到临时 OSS
3. 得到 `oss://...`
4. 提交 REST 识别任务时自动带 `X-DashScope-OssResourceResolve: enable`

### 5.4 文件转写与实时输入的边界

这是现在最重要的一个结论：

1. 文件转写已经不占用本地实时服务端 WebSocket
2. 文件转写直接在客户端完成上传、提交、轮询、结果保存
3. 所以 Rust/Tauri 新项目完全可以把文件转写做成独立后台任务模块

### 5.5 文件转写链路里当前没有做的事

虽然你在实时输入里用到了热词，但文件转写链路里当前并没有复用这套热词后处理。

当前文件链路做的是：

1. 解析百炼返回的 `transcripts/sentences/words`
2. 直接落盘

它不会：

1. 做热词纠错
2. 做规则替换
3. 做 LLM 角色处理
4. 做打字/粘贴输出

所以如果你以后希望“文件转写结果也做热词修正”，那在新项目里需要明确把这件事作为新增需求，而不是默认照搬当前行为。

这些在你现在的真实使用里不是刚需。

1. 本地模型：`fun_asr_nano / sensevoice / paraformer`
2. LLM 角色系统
3. 纠错历史给 LLM 做上下文
4. UDP 广播
5. UDP 控制录音
6. 繁体转换
7. 保存原始录音音频

这次重构时不要把“仓库里存在”误当成“当前主流程在用”。

例如下面这些不是当前两条主链路的核心：

1. `config_client.py`
2. `config_server.py`
3. `util/client/transcribe/result_handler.py`

它们更多是旧链路残留或边缘模块，不应在 Rust 重构时抢占优先级。

## 7. 当前默认会参与执行、但你主观上可能没在“使用”的附属能力

这是最容易在重构时漏掉的部分。

### 7.1 LLM 系统会初始化

即使你没主动用 LLM，只要：

1. `Config.llm_enabled = True`

启动时就会：

1. 初始化 LLM 角色
2. 启动文件监视

但如果语音文本没有角色前缀，最终又会退化成普通输出。

所以它的状态是：

1. 当前默认参与启动
2. 但不属于你当前核心需求

### 7.2 文字备份会默认执行

当前默认：

1. `save_text_backup = True`

所以每次最终识别成功后，都会把文字写进 `YYYY/MM/DD.md`。

这不是“上屏功能”的一部分，而是一个旁路持久化副作用。

### 7.3 UDP 广播默认开启

当前默认：

1. `udp_broadcast = True`

也就是每次最终输出文本后，都会向本地广播地址发一份 UDP 消息。

如果你没有外部程序消费它，这在新项目第一版里可以先砍掉。

### 7.4 托盘默认开启

服务端和客户端都默认启用托盘。

但从你的真实需求看，托盘只是交互包装层，不是识别链路本体。

## 8. 当前系统最值得迁移的“核心协议与算法知识”

如果后面你要把这份文档喂给编码 AI，这一节是价值最高的部分。

### 8.1 实时链路的会话抽象

当前正确抽象不是：

1. 一个片段一次识别

而是：

1. 一次按下到抬起
2. 就是一整个云端识别会话

### 8.2 云端结果不是增量文本，而是句子快照

必须保留这条认知：

1. `result-generated` 对同一句可能会反复更新
2. 不能直接把每次 `text` 追加到总文本里

### 8.3 必须等待会话结束确认

当前稳态成功路径是：

1. 持续送音频
2. 发送 `finish-task`
3. 等待 `task-finished`
4. 汇总最终文本

### 8.4 失败时不能把已定稿内容全丢

当前系统做得对的一点是：

1. 即使最后 finish 失败，也会保留已定稿句

这个思想应该保留到 Rust 版。

### 8.5 热词是客户端后处理，不是云端热词表

当前热词逻辑发生在客户端结果处理阶段，而不是：

1. 服务端识别前注入词表
2. REST 提交时使用 `vocabulary_id`

所以它本质上是“识别后的纠错层”。

## 9. Rust/Tauri 重构建议

这部分结合了当前代码现状，以及 Tauri 2 官方推荐的“Rust 后端命令 + 前后端事件/通道”的架构思路。

### 9.1 推荐的新项目形态

建议新项目直接做成“单个 Tauri 应用 + Rust 后台任务”，而不是继续保留“本地 client/server 双进程”。

原因：

1. 当前 client/server 拆分主要是历史产物，服务端原本用于承接本地模型。
2. 现在你的核心识别已经走云端。
3. 文件转写也已经证明：不靠本地服务端也能独立跑通。

### 9.2 推荐的模块边界

#### Rust 后端

建议放这些模块：

1. `shortcut_service`
全局快捷键注册、按键状态机。

2. `audio_capture_service`
麦克风采集、缓冲、重采样、单声道处理。

3. `realtime_asr_service`
阿里云百炼实时 WebSocket 会话管理、句子状态机、失败保底。

4. `file_transcribe_service`
FFmpeg 预处理、上传、REST 提交、轮询、结果解析。

5. `hotword_service`
热词文件加载、规则替换、音素纠错。

6. `text_output_service`
模拟打字、剪贴板粘贴。

7. `persistence_service`
日志、文字备份、失败任务保存。

#### Tauri 前端

建议只放这些页面或交互层：

1. 设置页
2. 热词编辑页
3. 文件拖放页
4. 任务状态/日志页
5. 可选托盘菜单入口

### 9.3 推荐的前后端通信方式

根据 Tauri 官方文档，建议这样分：

1. 前端主动触发的操作，用 `command`
例如：
   - 开始/停止文件转写
   - 打开热词文件
   - 保存配置

2. 后端持续推送的状态，用 `event` 或 `channel`
例如：
   - 文件转写进度
   - 实时识别状态
   - 错误提示
   - 日志更新

3. 全局快捷键、托盘等桌面能力优先用 Tauri 官方插件或 Rust 侧实现

### 9.4 推荐的重构顺序

#### 第一阶段：冻结协议与行为

先把这几个行为写成明确规范：

1. 按键长按/短按规则
2. 录音会话边界
3. 云端句子状态机
4. 最终文本输出规则
5. 文件转写的输入输出格式

#### 第二阶段：先写 Rust 核心库，不急着做漂亮 UI

先把这些做出来：

1. 实时会话模块
2. 文件转写模块
3. 热词模块
4. 文本输出模块

#### 第三阶段：再接 Tauri 外壳

把 Rust 核心接入：

1. 全局快捷键
2. 配置页面
3. 文件拖放页面
4. 日志页面

#### 第四阶段：最后补附属能力

例如：

1. 托盘
2. 文字备份浏览
3. 失败任务重试界面
4. LLM 系统

## 10. 建议给编码 AI 的“项目边界描述”

如果你后面要把这份文档喂给编码 AI，可以直接把下面这段作为任务边界说明。

### 10.1 新项目目标

用 `Rust + Tauri` 重写一个桌面语音输入工具，只保留当前 fork 中真实使用的两条核心能力：

1. 实时语音输入  
按住全局快捷键录音，松开结束；使用阿里云百炼实时 WebSocket 识别；识别完成后做热词替换并直接打字或粘贴输出。

2. 文件转写  
支持把音频或视频文件拖入应用窗口；应用先把文件转成 16k 单声道 wav，再上传到百炼支持的 URL；调用百炼 REST 异步接口轮询结果；最后保存 `.txt/.json/.srt`。

### 10.2 当前必须保持一致的行为

1. 实时链路按“整次按下/抬起”为单个云端会话处理。
2. 云端 `result-generated` 必须按句子状态机覆盖更新，不能直接追加。
3. 只有在结束并确认后，才把最终文本回传给输出层。
4. 热词替换发生在最终文本阶段，而不是云端识别前。
5. 文件转写是独立后台任务，不应阻塞实时输入。

### 10.3 当前可以暂时不做的能力

1. 本地模型
2. LLM 角色
3. UDP 广播/控制
4. 繁体转换
5. 录音文件保存
6. 托盘增强菜单

## 12. 最终建议

这次 Rust/Tauri 重构最该抓住的不是“把 Python 模块翻译过去”，而是抓住下面这几个不变的业务真相：

1. 你真正要的只有两个功能：实时输入、文件转写。
2. 当前实时链路最有价值的资产是“云端会话状态机”，不是 Python 代码形式本身。
3. 当前文件链路已经天然适合改成 Tauri 内部后台任务。
4. 当前很多默认启动能力并不是你核心需求，第一版完全可以砍掉。
5. 新项目最合理的形态是“单个 Tauri 应用内部完成全部核心流程”，而不是继续保留独立本地 server。

如果后面继续推进，下一步最值得做的不是马上写 Tauri UI，而是先把这份文档进一步收敛成一份“Rust 核心模块接口设计稿”，也就是把：

1. 输入
2. 输出
3. 状态机
4. 错误模型
5. 配置结构

全部冻结成 Rust 风格的数据结构与 trait 边界。
